Architecture Decisions
What

Implement SAPLING_EMPTY_STATE and SAPLING_VERIFY_UPDATE in MIR (the Michelson-in-Rust interpreter) for the Tezos X kernel. These instructions enable privacy-preserving transactions using the Zcash Sapling protocol — shielded transfers where amounts and parties are hidden behind zero-knowledge proofs (Groth16 over BLS12-381).

How: Hybrid Architecture

MIR owns all validation logic (type checking, nullifier tracking, memo size enforcement, verification orchestration). The kernel provides cryptographic primitives and storage via a SaplingBackend trait. This keeps MIR independent of zcash_primitives while allowing full unit testing with mocked crypto.

Scope
  • No deprecated support — SAPLING_VERIFY_UPDATE_DEPRECATED and sapling_transaction_deprecated are excluded. Tezos X is a fresh chain with no legacy contracts.
  • octez-client compatibility required — shield, unshield, transfer, and balance scanning must work using existing client commands pointed at the Tezos X RPC endpoint.
  • L1 conformity — identical accept/reject decisions, identical final state, identical balance for any Michelson program using Sapling instructions.

Decision Details

D1: No deprecated support

SAPLING_VERIFY_UPDATE_DEPRECATED and sapling_transaction_deprecated are NOT implemented. Tezos X is a fresh chain — no legacy contracts exist. If migration from L1 is needed later, deprecated support can be added as a separate work item.

Deprecated transactions differ by lacking the bound_data field (replaced with empty string when cast to current format in L1).

D2: Hybrid architecture (Option C)

MIR owns the logic, kernel provides the crypto and storage. Three options were considered:

  • Option A: Everything in MIR — rejected because MIR gains a heavy dependency on zcash_primitives
  • Option B: Everything in kernel — rejected because MIR loses control of validation logic
  • Option C (chosen): Hybrid — MIR controls orchestration, kernel provides primitives via trait

The associated type VerificationCtx allows the kernel to use an opaque Rust-allocated context while the mock uses a simple counter.

D3: Unified SaplingBackend trait

One trait combining 5 crypto methods, 5 storage methods, and 1 diff application method. MIR controls the orchestration order: outputs first, then inputs, then final_check. This order is cryptographically required — the verification context accumulates commitment values (cv) from each call.

D4: Minimal SaplingState

SaplingState contains only id (negative=temp, positive=persisted), memo_size (u16, immutable), and diff (write buffer). No tree, no root buffer. Tree and nullifier storage live behind the SaplingBackend trait.

Type properties (verified against L1): dupable=YES, packable=NO, comparable=NO, big_map value=NO, allowed in views=YES.

D5: Validator orchestration in MIR

sapling_verify_update orchestrates 5 verification steps:

  1. Memo size check (MIR, no backend call)
  2. Root membership (backend: root_mem)
  3. Nullifier check + accumulation in diff (backend: nullifier_mem + diff check)
  4. ZK proof verification (backend: new_ctx → check_output → check_spend → final_check)
  5. Commitment accumulation in diff (MIR, no backend call)

Critical: Root is NOT calculated during verify_update — it's calculated in apply_diff after execution. A 2nd verify_update in the same call cannot use a root from the 1st.

D7: Encoding via tezos_data_encoding

Use tezos_data_encoding with derive macros (BinWriter, NomReader). Already a dependency of MIR and the kernel. Exception: Ciphertext needs a manual impl because payload_enc size depends on the contextual memo_size (= memo_size + 67 bytes).

D9: Merkle tree maintained by backend only

MIR never touches the Merkle tree. The backend handles insertions and root computation in apply_diff. Uncommitted hashes (32 precomputed values for the empty tree) are initialized at backend startup. The tree has a fixed height of 32, supporting up to 2^32 (~4 billion) commitments.

Root retention uses a circular buffer of 120 entries. Only ONE root per block level — prevents intra-block transaction chaining.

D14: Durable storage layout 
/tezlink/sapling/<id>/
  /tree/<node_position>             → hash (32 bytes)
  /tree_size                        → u64
  /ciphertexts/<position>           → ciphertext (variable)
  /nullifiers/hashed/<nf_hex>       → empty (existence check)
  /nullifiers/ordered/<index>       → nf (32 bytes)
  /nullifiers/size                  → u64
  /roots/buffer/<index>             → root hash (32 bytes)
  /roots/pos                        → u32 (circular buffer position)
  /roots/level                      → block level
  /memo_size                        → u16

Dual nullifier indexing: hashed/ for O(1) membership check during verify_update, ordered/ for sequential scan by the RPC. SafeStorage handles rollback automatically (paths under /tezlink/).

Trait Design: SaplingBackend

trait SaplingBackend {
    type VerificationCtx;

    // Crypto -- verification context lifecycle
    fn new_verification_ctx(&self) -> Self::VerificationCtx;
    fn check_output(&self, ctx: &mut Self::VerificationCtx, output: &Output) -> bool;
    fn check_spend(&self, ctx: &mut Self::VerificationCtx,
                   input: &Input, root: &[u8; 32],
                   anti_replay: &str) -> bool;
    fn final_check(&self, ctx: &Self::VerificationCtx,
                   balance: i64, binding_sig: &[u8; 64],
                   anti_replay: &str) -> bool;
    fn merkle_hash(&self, height: u32,
                   a: &[u8; 32], b: &[u8; 32]) -> [u8; 32];

    // Storage -- state access
    fn root_mem(&self, id: &SaplingStateId, root: &[u8; 32]) -> bool;
    fn nullifier_mem(&self, id: &SaplingStateId, nf: &[u8; 32]) -> bool;
    fn add_commitments(&mut self, id: &SaplingStateId,
                       cms: &[(Commitment, Ciphertext)]) -> [u8; 32];
    fn add_nullifiers(&mut self, id: &SaplingStateId,
                      nfs: &[[u8; 32]]);
    fn add_root(&mut self, id: &SaplingStateId, root: &[u8; 32]);

    // Diff application (called by kernel after successful execution)
    fn apply_diff(&mut self, id: &SaplingStateId,
                  diff: &Diff) -> Result<(), SaplingError>;
}
Verification Order Is Cryptographically Required

Outputs checked first, then inputs (spend proofs + signatures), then binding signature. The verification context accumulates commitment values (cv) from check_output and check_spend calls. final_check uses these accumulated values to validate the binding signature. Changing the order would cause final_check to fail on valid transactions.

Risk & Mitigations

R1: PACK Conformity for bound_data (L2-1055)

Risk: For unshield operations, bound_data contains the destination PKH packed via Michelson PACK. If our PACK encoding diverges from L1 (known issue L2-1055 with comb pair encoding), unshield transactions forged by octez-client will fail verification on Tezos X.

Mitigation: L2-1055 must be resolved before unshield can work with octez-client. Shield and transfer operations are unaffected (bound_data is empty).

R2: WASM Memory Budget for Parameter Files

Risk: Parameter files consume ~50 MB of the kernel's WASM linear memory (max 4 GiB). Loaded once at startup, not reclaimed.

Mitigation: 50 MB is ~1.2% of max memory. Files are loaded lazily at first SAPLING_VERIFY_UPDATE, not at boot. SAPLING_EMPTY_STATE does not need parameter files.

R3: Silent Failure on Corrupted Parameter Files

Risk: L1 does NOT validate parameter file checksums. Corrupted files load without error but produce cryptographically invalid results — verification silently fails on valid transactions or silently succeeds on invalid ones.

Mitigation: Our implementation adds SHA-256 checksum validation at initialization (stricter than L1). Corrupted files produce a clear error, not silent misbehavior.

R4: Root Buffer Duration Depends on Block Time

Risk: Root buffer of 120 entries. L1 assumes ~10s blocks = ~20 min validity. If Tezos X kernel produces blocks faster (e.g., 2s), window shrinks to 4 minutes. Forged transactions may expire before confirmation.

Mitigation: Root buffer size is an adjustable storage parameter (not cryptographic). Can be safely increased. Cost: 32 bytes per additional root per pool (negligible).

R5: Test Data Extraction from OCaml

Risk: Conformity tests (4.5, 4.6) require serialized intermediate values from OCaml test execution. No existing mechanism to dump binary intermediates from OCaml to files.

Mitigation: Instrument OCaml test suite to dump binary intermediates. Alternative: use octez-client to forge transactions and capture wire-format data.

R6: Max Transaction Size

With memo_size = 65535 and 2,019 outputs, a single Sapling transaction can be ~130 MB. Worst-case gas: ~140M units (exceeds L1 per-block limit of ~15M). In practice, transactions are small (1-5 inputs, 1-3 outputs). The kernel gas model must account for worst-case costs.

Key Non-Functional Insights
  • Determinism: Verification is pure (no OS entropy, no floating point). Proving is intentionally non-deterministic (client-side only). Safe for WASM kernel consensus.
  • Storage growth: A pool with 1M commitments (memo_size=8) requires ~367 MB of durable storage.
  • Privacy leakage: Transaction input/output counts and bound_data are NOT encrypted. Unshield operations reveal the recipient PKH.
  • Recursion safety: All L1 recursive functions are safe to port. Tree-depth functions (32 levels) are safe without TCO. List-recursive functions should be rewritten as iterative — trivial transformations.
  • No upgrade path: Changing the proof system (Groth16 to another) requires a new pool. Existing state cannot be migrated. Spec version is hardcoded at 2020.1.2.
